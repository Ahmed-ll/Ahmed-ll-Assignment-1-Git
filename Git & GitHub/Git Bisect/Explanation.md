# Git Bisect

##### الفكرة هي اني بستخدم *Git Bisect* عشان أحدد الـ *commit* اللي تسبب في ظهور *Bug*، عن طريق إن Git بيعمل *Binary Search* بين الـ commits بدل ما أراجع كل الـ commits واحد واحد.

مثال دلوقتي احمد شغال على مشروع، وكل حاجة كانت شغالة بشكل طبيعي، لكن فجأة اكتشف إن فيه **Bug** ظهر في آخر نسخة من المشروع.

واحمد عارف إن:

- آخر commit فيه الـ **Bug**.
- لكن فيه commit قديم كان المشروع فيه شغال بشكل طبيعي.

مثلاً عندنا الـ **history** ده:

```
A---B---C---D---E---F---G
            ↑           ↑
         Good         Bad
```

بحيث:

-  ان `D` هو آخر commit احمد متأكد إن الـ **Bug** مش موجود فيه.
- وان `G` هو آخر commit والـ **Bug** موجود فيه.

بدل ما احمد يراجع الـ commits:

```
E → F → G
```

واحد واحد، يقدر يستخدم **Git Bisect**.

أول حاجة يبدأ الـ **bisect**:

```bash
git bisect start
```

وبعدها يقول لـ **Git** إن الـ commit الحالي فيه الـ **Bug**:

```bash
git bisect bad
```

وبعدين يرجع للـ commit اللي احمد متأكد إن المشكلة مش موجودة فيه، ويقول لـ **Git** إنه **Good**:

```bash
git bisect good D
```

بكده **Git** هيبدأ يعمل **Binary Search** بين الـ commits، وهيختار commit في النص ويخلّي الـ repository واقف عليه.

مثلاً:

```
A---B---C---D---E---F---G
            ↑       ↑
          Good    Git checks
```

احمد دلوقتي يشغل المشروع ويختبر هل الـ **Bug** موجود ولا لأ.

لو الـ **Bug** موجود، يقول لـ Git:

```bash
git bisect bad
```

ولو الـ **Bug** مش موجود، يقول:

```bash
git bisect good
```

و**Git** هيكرر نفس العملية، وفي كل مرة بيقلل عدد الـ commits اللي محتاج نختبرها للنصف تقريبًا.

وفي النهاية **Git** هيحدد الـ **commit** اللي تسبب في ظهور الـ **Bug**.

بعد ما احمد يعرف الـ commit المسؤول، يقدر ينهي عملية الـ **bisect**:

```bash
git bisect reset
```

وبكده بنستخدم **Git Bisect** لما نكون عارفين إن الـ **Bug** موجود في commit معين حاليًا، لكن مش عارفين **ظهر لأول مرة في أنهي commit**، وGit بيساعدنا نحدد الـ commit ده بسرعة باستخدام **Binary Search** بدل ما نراجع كل الـ commits واحد واحد.
